MeetPoint：预算受限的双人会合规划 Agent
两个人从不同地方出发，通勤上限和偏好也不同，约一个双方都方便的见面地点往往需要反复比较。MeetPoint 将双方要求转为结构化条件，查询候选商场及公共交通路线，在明确的调用预算内筛选并推荐可行方案，支持多轮修改和重新规划。

第一版支持北京市、两人、公共交通、商场。推荐只覆盖本次实际查询的候选，不保证全城最优；预算内未找到方案也不等于全城无解。
主要能力
- 双方约束分别检查：各自设置最长通勤时间、最大换乘次数和步行距离。必需数据未知时保留未知，不按0计算。
- 先校验，再排序：先从满足个人限制的路线中选择路线，再检查双人方案，进行 Pareto 筛选和确定性排序，最多展示3个方案。
- 根据反馈继续搜索：首轮搜索中间区域，之后模型依据失败反馈和剩余预算，选择向A侧、向B侧补查、扩大半径、追问或结束。搜索坐标与半径由代码计算。
- 结构化 Memory：保存已确认条件及其版本，只更新用户明确修改的字段。显式长期偏好、本次条件和默认值有明确优先级，支持查看、修改和删除偏好。
- 预算与错误边界：限制地图请求、模型调用、搜索轮数和每轮新增候选数；区分无路线、缺数据、接口错误、等待确认和预算结束。
- 过程可查看：单文件页面展示条件、候选卡片、搜索动作、排除原因、调用统计和停止原因。
例如“我这次可以接受60分钟”只修改A在当前任务中的时间上限；“以后默认最多换乘0次”才修改长期偏好。初版条件修改支持明确字段和受控句式，未实现任意自然语言的通用需求解析。
实现方式
模块	技术与职责
接口与校验	Python、FastAPI、Pydantic：校验条件、参数、版本和动作
外部工具	高德 Web 服务 API、httpx：地点解析、商场搜索、公共交通路线查询
Agent 循环	LangGraph：根据工具结果继续搜索、追问或停止
模型接入	OpenAI兼容SDK；本次实测配置及返回模型均为 qwen3.8-27b
确定性规划	Python：硬约束、路线选择、Pareto筛选、偏好排序及预算预扣
状态保存	SQLite：任务条件、显式偏好、运行计数和控制检查点
展示与运行	单文件HTML、Docker Compose、unittest


模型主要负责选择后续搜索动作。路线数值、硬约束判断和推荐排序由代码处理。两种排序分别优先比较双方较长的通勤时间，或两人的总通勤时间，再按固定规则比较其他指标。

默认每次规划最多3轮搜索，每轮最多5个新候选，地图HTTP最多40次、模型调用最多12次；重试也计入预算。已评估的完整可行候选达到3个时结束探索，这不保证 Pareto 筛选后仍有3张推荐卡片。

Memory优先级为：本轮明确要求 > 当前任务已确认条件 > 显式长期偏好 > 默认值。长期个人限制仅作用于本人A。条件更新后旧运行失效，不能把旧方案当作新要求的完成结果。

地图候选和路线保留在本次运行的临时内存中，不进入业务表、持久消息历史或图检查点。恢复会话时读取已确认条件，再重新查询路线。
本地启动
需要Docker Desktop及Docker Compose。首次配置时将 .env.example 复制为 .env，填写自己可用的地图和模型Key；已有可用配置时沿用原 .env。
docker compose config --quiet
docker compose up -d --build app
打开 本地演示页面。修改 .env 后，通过以下命令重新加载运行环境：
docker compose up -d --force-recreate app
本地演示用户标识用于区分任务和偏好，目前未提供生产环境的身份认证与权限体系。
